## Other foreign-code and packaged surfaces

- libxml2, OpenSSL, zlib, ncurses and `lib/regex/regex.c` are separate foreign-code inputs. This C++ audit does not call them Rust implementations or infer their complete language makeup from target names. Application adapters and outstanding full-operation migration contracts still need to be retired or explicitly accounted for. In particular, Rust NZB metadata helpers do not replace the current libxml2 SAX caller.
- Windows/macOS/Android build and packaging scripts still build or package the C++ application. Mandatory Rust target/toolchain/build selection must replace the optional POSIX-only integration before a platform can be checked off.
- The macOS app contains seven Objective-C implementations under `platforms/macos`: `DaemonController.m`, `MainApp.m`, `PFMoveApplication.m`, `PreferencesDialog.m`, `RPC.m`, `WebClient.m`, and `WelcomeDialog.m`. Each now has its own unchecked Rust-replacement/platform-validation row in the completion checklist and an immutable blob in `dependency-sources.json`. Preserve their UI, daemon, preferences, installation and RPC lifecycle contracts. Their distinct language is not included in the daemon C++ filename count; native macOS proof and any explicitly reviewed scope decision remain pending.
- Windows, Android and macOS packaging can download UnRAR/7zip tools, while daemon unpack controllers invoke external commands. These binaries are distinct from linked daemon libraries. Inventory exact selected package assets and their implementation languages before claiming the complete distributed product is C++-free; removing a linked library does not retire a bundled external executable.
- Windows resource headers and installer/resource scripts are build inputs, not automatically C++ algorithms. Carry their constants/assets into the replacement packaging path without deleting needed resources merely because a file has a `.h` suffix.
