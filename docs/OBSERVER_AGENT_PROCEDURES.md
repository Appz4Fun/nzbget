## Observer correctness and evidence procedures

- Verify behavior against the exact canonical daemon commit using `git show COMMIT:FILE`; a stale checkout is not the deployed or target implementation. Preserve the original head and each failed attempt before repairing source.
- Check scheduling and in-flight worker behavior separately. A global pause flag can prevent starts without stopping work already in progress. Force-priority article/post jobs use the daemon threshold; URL fetching has a different coordinator. Never infer per-job inactivity from global flags alone.
- Require an observable progress signal for an unchanged-progress detector. The current URL downloader keeps received-byte progress locally, so its FETCHING stage cannot establish a stall from article/post counters. Adding a new daemon signal requires separate scope; a watcher can conservatively exclude unsupported stages.
- NZBGet RestrictedUsername/RestrictedPassword is not a read-only credential: restricted RPC denies saveconfig while permitting queue-changing methods. The watcher sends only status/listgroups. Enforced read-only access requires actual method filtering with daemon credentials held at that boundary; do not imply the tool installs a proxy.
- Preserve missing/invalid values as unknown. Validate signed priority and unsigned high/low words, stage allowlists, duplicate IDs, and response/job limits. Preserve original malformed RPC replies and remote errors in access-restricted private evidence before parsing; retain raw successful replies privately when required by the frozen capture plan. Keep raw replies, names, destinations, article IDs, and error text out of shared exports or redact a separate derivative. Avoid credential capture; if unavoidable, restrict access to the original. Exclude credentials from exports. Status/listgroups replies are sequential, not an atomic snapshot.
- Derive regression expectations from daemon contracts, not the observer implementation. Exercise real normalize-to-Detector behavior for force threshold boundaries, ordinary and force pauses/quota, running versus queued/finished stages, malformed values, progress changes, restart evidence, and alert deduplication. Observe expected test failures before production changes, then run the full standalone crate suite.

## Measurement boundaries

- Keep collection cost, daemon observer effect, and Rust migration qualification distinct. A synthetic loopback client experiment including startup does not measure daemon overhead or production throughput. Historical timings remain bound to their original source/binary; a later correctness fix does not silently inherit them as new measurements.
- Complete-caller comparisons include allocations, copies, FFI, formatting, output, and destruction. Preserve current production C++ and clearly label algorithm-equivalent optimized C++ diagnostics. Use small/typical/large cases, raw paired CPU/wall measurements, build/process-aware uncertainty and prospective effect bounds. Keep regressions and inconclusive controls held.
- Continuous collection should be inexpensive and bounded; investigate a specific symptom with a short capture and an uninstrumented control. Linux observations describe the watcher-visible host/namespace unless deployment identity is separately established. PSI indicates contention, not its cause; cumulative counters need deltas.
- Local source status, tests, independent review, exact-head CI/review, merge, deployment and live verification are separate gates. Earlier tiny PAR fine-attribution overhead remains historical HOLD evidence and does not justify repeating per-byte profiling. Diagnostic instruction/call/allocation counts are not native latency or a speedup claim.
